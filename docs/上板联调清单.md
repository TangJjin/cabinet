# 上板联调与故障定位

这份清单是待实板执行的验收步骤，电脑编译和仿真通过不代表以下项目已经实测。

## 1. 先让双核和屏幕运行

1. 备份现有板内固件与需要的 QSPI 数据，确认目标是慧勤智远 STM32H747XIH6 CB V1.1。
2. 按 README 编译、合并四个 HEX，ST-LINK 连接并写入后校验。首次迁移使用完整内部 Flash 擦除与四目标烧录。
3. 检查双核启动选项和两个固定启动地址。上电后应出现总览，模拟模式明确可见，默认约 25 ℃/50 %RH，双核通信正常。
4. 观察绿灯通道心跳。没有 TF 卡时相应状态可以未就绪；不能因此复位循环。
5. 检查四角触摸、页面切换、设置文本框和数字键盘。对已有屏幕方向不做盲目改动，先对照 `bsp_touch.c`、显示端原转置代码定位。

黑屏优先按顺序查：CM7 是否进入 Bootloader → CM4 是否停在启动门 → QSPI ID → 应用向量表/CRC → SDRAM 初始化 → DSI/LTDC → 面板 → 触摸。Bootloader 故障循环会使蓝色通道闪烁并保持两个应用停止。

调试时注意 IWDG1 已从 Bootloader 启动。长时间单步/暂停可能触发看门狗；需要单步时用 ST-LINK 调试设置冻结 IWDG1，做看门狗/回滚实验时恢复正常计时。不要把“调试暂停导致复位”当作采集任务故障。

## 2. 模拟报警与设置

- 恢复正常，点击“温湿度超限”，计时检查持续约 5 秒后报警。
- 消音后保持超限，应一直静音；再触发水浸，应重新响铃。
- 消音后恢复正常，再触发同类超限，应重新响铃；“重新响铃”可立即撤销确认。
- 将模拟温度改为 34 ℃应仍保留已触发温度报警，降至 33 ℃解除；湿度同理验证 80/75 的迟滞。
- 注入离线，三次轮询失败后产生传感器故障。恢复正常，应自动恢复采样。第一次失败起温湿度显示 `--`，不继续显示旧数值为有效值。
- 保存阈值、地址和模拟开关，等“已保存”后断电重启，检查参数保留。保存未完成时断电，应保留此前的一份有效参数记录。

## 3. 接真实输入输出

- 接高电平触发、带驱动的有源蜂鸣器模块。验证静音、间歇响铃以及上电默认不误响。
- 用干接点先将 PC13 拉低，稳定 200 ms 后应水浸报警；短脉冲不应触发。
- 接好 RS485 转换器和温湿度传感器，关闭模拟模式。确认供电、共地/隔离、地址、9600/8N1、A/B 极性、DE 与 /RE。
- 逻辑分析仪观察 PG14 请求，PG12 发送高电平必须覆盖最后一个停止位；检查接收完整 9 字节和 CRC。
- 断开 A/B 或传感器供电，确认离线告警但系统继续运行；重新连接应恢复。故障期间不应从过期温湿度解除已有报警。

## 4. TF 卡与日志

- FAT32 TF 插入后应显示就绪，每 10 秒出现一条 DATA 记录；触发/解除、消音和重启应有 EVENTS 记录。
- 先设置 RTC，核对 CSV 时间。未设置时必须明确 `UNSET`，不能误认为自动获得当前时间。
- 无卡、满卡、运行时移除、重新插卡：系统仍应能采集/报警，未保存日志计数增加，重新插卡后恢复挂载与后续写入。文件系统损坏需要在电脑上修复，不做自动格式化。

## 5. 升级与断电实验

先完成旧版稳定启动，再生成版本号不同、两核匹配的候选包。保留一份可恢复的 FACTORY.hex。

| 场景 | 预期 |
|---|---|
| 正常升级 | 两核一起变为新版本，持续健康运行约 10 秒后确认 |
| 改动包任一字节/错误板卡/不配对版本 | 拒绝升级，原应用继续运行 |
| TF 包缺失、截断或同版本 | 页面报失败，内部 Flash 不擦写 |
| 写入 QSPI 暂存区时断电 | 未提交请求时保持旧版，重新触发可再安装 |
| 备份旧版时断电 | 旧内部镜像仍在，下次重新完成备份 |
| 擦写 CM7 或 CM4 应用时断电 | 启动门阻止 CM4 应用运行；下次重新安装完整镜像对 |
| 新版连续三次未健康确认 | 第四次经过 Bootloader 时恢复上一对固件 |
| 回滚擦写途中断电 | 下次继续从完整 QSPI 备份恢复 |
| 已确认的新版本普通看门狗复位 | 仍启动已确认版本，不无条件回滚 |

可用调试器在试运行期间暂停 CM4 采集任务或 CM7 任一工作任务，退出调试冻结后观察监督任务停止喂狗。真实传感器离线不应触发看门狗，因为超时处理本身属于正常任务进度。

物理断电测试需要逐项记录板卡、供电、断电时点、重启次数、两核版本和最终校验结果。主机测试目前注入的是存储操作边界/半操作的模拟掉电，不能替代芯片实际擦写、Flash ECC 和电源斜率验证。

## 用 ST-LINK 重新部署后的 QSPI 元数据

应用自己覆盖内部 Flash 会与旧 QSPI 元数据中的 CRC 不一致，Bootloader 可能恢复备份或停在恢复循环。推荐正常开发迭代也通过 TF 升级包完成。

若必须回到全新的出厂状态：用兼容板上 QSPI 接线的编程算法，仅清除 QSPI 0x000000～0x003FFF（启动/配置元数据），再完整烧入配套 FACTORY.hex。务必先备份需要保留的参数和 QSPI 数据。当前工程没有自动擦除整个外部 Flash 的脚本，也不修改读保护/写保护/启动选项字节。

如果修改了分区、板卡 ID 或 OpenAMP 协议版本，需要一起重新部署四个目标，旧 Bootloader 不负责迁移这些格式。
